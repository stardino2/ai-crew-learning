# Harness Engineering 발표 대본

- 일시: 2026-05-20
- 청중: 부서 개발자 (FE / BE / System Engineer, AI 수준 다양)
- 분량: 10분 + Q&A
- 총 슬라이드: 21장

각 항목은 **슬라이드 화면 → 발표자 멘트 → (선택) 화면 동작**.
멘트는 그대로 외우기보다 한 번 읽고 톤만 가져가시면 됩니다. 시간은 누적이 아니라 슬라이드 당 권장 길이입니다.

---

## 1. 표지 — Harness Engineering (0:00–0:25, ~25s)

> 안녕하세요. 오늘 10분 동안 짧은 개념 하나만 같이 보려고 합니다. **Harness Engineering**.
>
> 거창한 새 방법론을 소개하려는 게 아니라, AI가 만들어내는 결과를 우리가 평소처럼 *믿고 쓸 수 있게* 만드는 방법에 대한 이야기입니다.
>
> 화면에 보이는 한 줄이 오늘 핵심이에요. *AI 결과 → 검증 기준 → 신뢰 가능한 결과.* 이 사이를 어떻게 잇느냐가 주제입니다.

---

## 2. 이게 하네스입니다 (0:25–0:55, ~30s)

> 먼저 **하네스**라는 단어부터 짚고 갈게요. 사진 보시면 강아지가 이런 줄을 매고 있죠. 이게 하네스입니다.
>
> 원래는 무언가가 *제멋대로 움직이지 않게* 잡아주는 장치예요.
>
> 오늘 이 발표에서는 **AI가 만든 결과가 팀의 검증 기준 안에서만 움직이도록 잡아주는 장치**라는 의미로 쓰겠습니다. 단어 자체는 비유고, 진짜로 다룰 건 검증 흐름이에요.

---

## 3. 퀴즈 — 병목은 어디일까요? (0:55–1:25, ~30s)

> 본론 들어가기 전에 가벼운 퀴즈 하나.
>
> AI를 활용해서 업무를 처리할 때, **병목은 어디에서 생길까요?**
>
> 화살표 따라가시면, 왼쪽도 AI가 빠르게 처리하는 일들이고 오른쪽도 마찬가지예요. 코드 수정, 테스트 실행, 빌드 결과 확인, 운영 공지… 다 AI가 도와줄 수 있는 일들이죠. 그런데 이걸 잇는 가운데 물음표 자리, 누구일까요?

*(3–5초 정도 청중 반응을 기다린 뒤 다음 슬라이드.)*

---

## 4. 정답 — 사람 (1:25–2:00, ~35s)

> 네, **사람**입니다.
>
> AI는 양쪽의 일들을 다 빠르게 만들어낼 수 있어요. 그런데 그 결과가 진짜 쓸 만한지 매번 *사람이 확인해야 하는 구조*가 되면, 결국 사람이 병목이 됩니다.
>
> 화면 마지막 줄이 핵심이에요. **반복 검증이 사람에게 몰리면 AI를 써도 흐름은 빨라지지 않습니다.** AI를 더 빠르게 만들수록 사람 줄만 더 길어져요.

---

## 5. 사람 검증을 자동 기준으로 (2:00–2:50, ~50s)

> 그래서 해야 할 일은, 사람이 매번 보던 것들을 **팀의 자동 검증 기준으로 옮기는 것**입니다.
>
> Before/After를 먼저 보시면, Before는 AI 변경이 있을 때마다 사람이 매번 보고 머지하는 흐름이에요. After는 AI 변경이 자동 검증 기준을 지나가고, 사람은 예외만 판단합니다.
>
> 아래 표가 더 구체적이에요. 왼쪽은 우리가 PR 리뷰할 때 묻는 질문들입니다. "테스트 돌렸나?", "설정 형식 맞나?", "API 계약 깨졌나?", "운영 공지 갱신했나?", "화면에 보이나?" — 이걸 매번 사람이 묻는 대신, 오른쪽처럼 CI, schema validation, contract test, docs check, UI smoke check로 옮겨두는 거예요.
>
> 사람은 *매번 보는 사람*이 아니라, *기준을 설계하고 예외만 판단하는 사람*이 됩니다.

---

## 6. 정의 — Harness Engineering (2:50–3:20, ~30s)

> 정리하면, **Harness Engineering**은 AI가 만든 결과를 사람이 매번 손으로 검증하는 대신, *팀의 자동 검증 기준을 통과하게 만드는 일*입니다.
>
> 그림으로 보면, 가운데 AI 변경이 있고 둘레에 build, test, review, ops, docs 다섯 개의 관문이 있어요. AI가 만든 변경이 이 다섯 개를 자동으로 지나갈 수 있게 만드는 게 하네스가 하는 일입니다.

---

## 7. 공개 자료에서 보이는 공통 패턴 (3:20–3:55, ~35s)

> 이 용어가 완전히 정착된 건 아니에요. 다만 공개된 자료들을 보면 같은 방향을 가리킵니다.
>
> OpenAI는 *테스팅·검증·리뷰·피드백·복구를 시스템에 박아두라*고 말하고, Claude Code는 CLAUDE.md와 hooks·skills로 저장소별 규칙을 제공해요. GitHub Copilot은 GitHub Actions와 PR 흐름 위에서 에이전트가 작업하게 하고, DORA가 오래전부터 말해온 자동 테스트·배포 자동화·빠른 피드백도 사실 같은 방향이에요.
>
> 위에 한 줄이 핵심입니다. *에이전트에게 지시만 주는 게 아니라, 저장소 규칙·훅·CI·리뷰 루프를 함께 제공한다.*

---

## 8. 이번에 만들 변화 (3:55–4:25, ~30s)

> 이제 짧은 시연을 보겠습니다. 먼저 무엇을 만들 건지부터.
>
> 왼쪽이 **현재** 상태 페이지예요. 서비스 목록만 보이는 평범한 화면입니다.
>
> 오른쪽이 **목표**예요. 차이는 가운데 노란 점검 배너 하나입니다. *API Gateway에 예정 점검이 있다*는 사실을 첫 화면에서 바로 보이게 만드는 거예요.
>
> 이 변화를 AI에게 한 번에 요청하면 어떤 흐름이 일어나는지 보여드릴게요.

---

## 9. HTML 시연: mini-status-harness (4:25–4:55, ~30s)

> 프롬프트는 보시는 그대로예요. 점검 시간, 영향 서비스, 첫 화면에 보여야 한다, 운영 공지도 같이 갱신해라. 사람이 평소에 동료에게 부탁하듯 한 줄로 적었습니다.
>
> 아래 8단계가 지금부터 이어집니다. **베이스라인 → 요청 → 변경 → 하네스 → 실패 → 재요청 → 통과 → 리포트.**

*(영상이 있다면 여기서 영상 재생. 영상 없이 슬라이드로 갈 경우 10~17번 슬라이드를 차례로 짚어주시면 됩니다.)*

---

## 10. 시연 전 — 베이스라인 HTML (~20s)

> 이게 시작점입니다. 점검 배너 없는 정상 상태 페이지예요.
>
> 어떤 자동화도 들어가지 않은 평범한 화면이고, 여기에 점검 안내를 더하는 게 이번 작업입니다.

---

## 11. 시연 1 — 요청 (~15s)

> 사람은 체크리스트를 풀어서 설명하지 않습니다. 원하는 **운영 상태**를 한 번에 요청해요.
>
> 점검 시간, 영향 서비스, 화면 노출 위치, 공지 갱신 — 이 네 줄이 전부예요.

---

## 12. 시연 2 — AI 변경 (~25s)

> AI는 한 파일만 만지지 않습니다.
>
> **config**에 점검 일정과 영향 서비스를 박고, **UI**에 배너 DOM과 스타일을 추가하고, **ops** 공지와 changelog를 갱신하고, **evidence**로 하네스 로그와 화면 캡처까지 남깁니다.
>
> 변경은 config, UI, 문서, 증거 산출물까지 묶여서 이어져요. 사람이 평소에 "이 정도면 됐다" 싶으면 빼먹는 것들까지 한 번에.

---

## 13. 시연 3 — 하네스 실패 (~25s)

> 여기서 하네스가 한 번 막아요.
>
> 운영 공지에 점검 날짜 "2026-05-20"이 빠져 있다고 알려줍니다. config는 그 날짜를 가지고 있는데 공지에는 없는 거죠.
>
> 메시지가 중요해요. *하네스는 AI를 막는 장치가 아니라, 빠진 운영 조건을 즉시 드러내는 장치입니다.* 실패가 결함이 아니라, 검증이 작동하고 있다는 증거예요.

---

## 14. 시연 4 — 실패 메시지를 다시 전달 (~25s)

> 그 다음이 재미있어요. 사람이 직접 고치는 게 아니라, **실패 메시지 자체를 다음 작업 지시로** AI에게 다시 넘깁니다.
>
> AI는 docs/ops-notice.md와 CHANGELOG.md를 config 기준 날짜·서비스명에 맞춰 보정해요.
>
> 핵심은 실패가 사람에게 돌아오지 않고, *실패 메시지가 곧 다음 작업 지시가 되는* 흐름입니다.

---

## 15. 시연 5 — 최종 통과 (~20s)

> 재요청 후 하네스를 다시 돌리면 lint, unit tests, config check, api contract, ui smoke, docs check가 차례로 통과합니다.
>
> 통과 기준은 단순해요. **UI, API, config, docs가 같은 운영 사실을 말하는가.** 한 곳이 어긋나면 다시 실패가 떨어집니다.

---

## 16. 시연 6 — 화면 확인 (~15s)

> 실제 화면에서도 API Gateway 예정 점검 배너가 첫 화면에 바로 보입니다.
>
> 처음 8번 슬라이드에서 보여드린 *목표* 화면 그대로예요.

---

## 17. 시연 7 — HTML 결과 리포트 (~25s)

> 마지막 산출물은 코드만이 아닙니다.
>
> 요청, 검증 결과, 화면 증거가 한 HTML 리포트에 묶입니다.
>
> PR 리뷰어가 코드 한 줄씩 따라가지 않아도, 이 리포트 하나면 *무엇을 요청했고, 어떤 검증을 통과했고, 화면이 어떻게 나왔는지*를 한눈에 확인할 수 있어요. 검증된 운영 가능한 변경 — 이게 하네스가 만들어내는 결과물입니다.

---

## 18. 역할별 적용 지점 (~45s, 7:30–8:15)

> 그래서 이걸 우리 팀 일에 어떻게 가져올 수 있을지 보겠습니다.
>
> **FE**는 UI smoke, 접근성, 화면 회귀를 자동 기준으로 둘 수 있어요. **BE**는 API contract, migration, compatibility 체크. **System Engineer**는 빌드 정책, 권한·감사, 배포 게이트. **운영·문서** 담당이라면 운영 공지, changelog, runbook 최신성을 자동으로 검증할 수 있습니다.
>
> 한꺼번에 다 하라는 얘기가 아니에요. 각자 자기 도메인에서 *사람이 매번 손으로 보고 있는 항목* 하나만 골라서 자동 기준으로 옮겨보시는 걸 권합니다.

---

## 19. 모델이 좋아지면 하네스는? (~40s, 8:15–8:55)

> 자주 받는 질문 하나. *"모델이 더 좋아지면 하네스 같은 거 필요 없어지는 거 아닌가?"*
>
> 오히려 반대입니다.
>
> 지금은 장황한 프롬프트와 사람 체크리스트로 떼우고 있지만, 모델이 좋아질수록 그 자리는 **테스트와 정책, hooks와 skills, 관측 가능성**으로 옮겨가요.
>
> 하네스는 사라지는 게 아니라 *얇고 정교하게 진화*합니다. 사람이 손으로 들고 있던 부분이 점점 코드로 박혀가는 거예요.

## 20. Harness가 천장을 받친다 (~50s, 8:55–9:45)

> 마무리하겠습니다.
>
> Andrej Karpathy가 한 말 인용할게요. **"Vibe Coding이 바닥을 올린다면, Agentic Engineering은 천장을 높인다."**
>
> 그런데 천장은 저절로 올라가지 않습니다. AI가 더 많이 만들수록 *검증·운영 부담도 같이 늘어나기* 때문이에요.
>
> Harness Engineering은 그 부담을 조직이 감당할 수 있게 만들어주는 도구입니다. 그래야 Agentic Engineering의 천장에 실제로 닿을 수 있어요.
>
> 한 줄로 가져가실 메시지. **AI에게 더 많이 맡기고 싶다면, 먼저 검증 흐름을 만드세요.**

## Q&A 백업 답변

**Q. "Harness Engineering"이라는 용어가 표준인가요?**
> 아직 정착 중인 용어예요. 다만 OpenAI가 글에서 명시적으로 쓰고 있고, Claude Code의 hooks·skills, Copilot의 PR 흐름, DORA의 capabilities가 가리키는 방향이 일관적이라 같이 묶을 수 있습니다.

**Q. 기존 CI랑 뭐가 달라요?**
> 도구는 비슷합니다. 차이는 *AI가 만든 변경을 1차 소비자로 둔다*는 점이에요. 사람이 한 번에 큰 PR을 올리던 시절의 CI와, AI가 하루에 수십 번 작은 변경을 시도하는 환경에서의 CI는 실패 메시지 디자인, 재실행 비용, 리포트 형태가 달라야 합니다.

**Q. 우리 팀에서 어디부터 시작하면 좋을까요?**
> 18번 슬라이드에서 자기 도메인에 해당하는 항목 하나만 골라보세요. 매번 PR에서 같은 질문을 묻고 있다면, 그게 가장 먼저 자동 기준으로 옮길 후보예요.

**Q. AI가 검증까지 알아서 할 수 있는 시대가 오면?**
> 19번 슬라이드 답변과 같습니다. 하네스는 사라지는 게 아니라 모델 안쪽으로 옮겨갑니다. 다만 *조직이 무엇을 옳다고 정의하는가*는 모델이 대신 결정해주지 않아요. 그 부분은 사람이 계속 들고 있어야 합니다.
